- 効果音と成長演出で飲み込み・成長の達成感を強める。

## 進め方

プロダクトオーナーが体験と仕様を決め、プロジェクトマネージャーが選択肢、技術リスク、実装範囲と検証結果を整理する。
細かい部品ごとにタスクを増やさず、遊んで評価できる単位で進める。
日程は仕様と最初の物理検証が固まってから見積もる。

## WP1: 1ステージを操作からクリアまで遊べる試作

### 最初のチェックポイント

必要最小限の環境で、穴の移動、中央追従カメラ、床の開口、小物・長い物・大きすぎる物の落下を確認する。
物理と見た目が成立するかを最初に判定する。大きなアセットや複数ステージは先に作らない。

床方式が成立しない、ブラウザ確認ができないなどの障害は根拠付きで報告し、
同じ不成立の試行を増やさず次の対応を決める。

### 遊べる範囲まで完成させる

成長ポイント、段階半径、カメラ後退、複数サイズの物、仮の目標物、クリア表示を繋ぐ。
再現可能なランダム配置を入れ、通常の操作だけで開始からクリアまで遊べるようにする。
数値は試作用の仮値を記録し、最終バランスとして扱わない。

完了条件:

- PCマウスとタッチ入力で穴を移動でき、入力が途切れても操作が残らない。
- 穴が画面中央にあり、成長前後でも画面上の大きさが一定に見える。
- 小物は落ち、大きすぎる物は支えられ、長い物の傾き・落下を観察できる。
- 回収ごとに一度だけ成長量が加算され、段階を跨ぐと実際の穴が拡大する。
- 目標物を飲み込んだ時だけクリアし、タイマー・失敗条件がない。
- 通常プレイで進行不能や床更新による不自然な落下がない。
- ビルド・必要なテスト・Lint・フォーマットと、ブラウザの確認結果を記録する。

## WP2: iPhoneでの操作と、開始から終盤までの負荷を検証する

対象端末と条件を定め、WP1の途中から早期にiPhone実機確認を始める。
物理挙動が成立してから、序盤・同時落下・終盤の負荷を測定する。

完了条件:

- iPhone Safariでドラッグ、成長、クリアを確認する。
- 縦横比、ブラウザUI、画面サイズ変更、バックグラウンド復帰で操作・表示が壊れない。
- 合意した端末と性能目標に対し測定結果がある。
- 必要な改善だけを実施し、傾き・落下・進行の副作用を確認する。

実機を利用できない場合は実機確認待ちとして記録する。PCやWebKitの自動テストで代替完了にしない。

## WP4: 公開に向けて整える

公開対象と品質基準をオーナーと決め、読み込み・互換性・エラー表示・必要な演出を整える。
保存、音、ステージ選択などは採用が決まったものだけを追加する。
配信先と公開手順を決め、公開操作は依頼・承認に基づいて実施する。

## 検証の重点

| 対象         | 検証方法                                                                                   |
| ------------ | ------------------------------------------------------------------------------------------ |
| 成長・クリア | 閾値の境界、複数段階の到達、最大段階、二重回収、目標物以外ではクリアしない単体テスト       |
| ステージ生成 | 同一シードの再現、初期重なり・境界、成長量不足、生成失敗のテスト                           |
| 物理的な落下 | 小物・長い物・大きすぎる物、穴の移動・成長、落下中の床変化を観察し、必要なケースだけ自動化 |
| 一連の体験   | 通常入力で移動 → 落下 → 成長 → 目標物 → クリアをブラウザ確認                               |
| 性能・互換性 | 条件を記録したPC・対象iPhoneの測定、初期化失敗・復帰時の確認                               |

チェックポイントごとに、実装内容、検証環境、結果、未確認事項と次の判断を記録する。
物理の細かな軌跡がブラウザを跨いで完全一致することは受け入れ条件にしない。
ビルドや単体テストの成功と、ゲームの面白さ・実機での快適さは別に評価する。
