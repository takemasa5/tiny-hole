# 技術構成と実装方針

更新日: 2026-10-14 / 状態: 推奨構成で試作を実装済み

追記: 同日のオーナー確認後、以下の推奨構成で試作を実装した。実際の採用範囲は [prototype.md](prototype.md) を参照。

## 推奨する構成

| 用途         | 推奨                                           | 理由                                                         |
| ------------ | ---------------------------------------------- | ------------------------------------------------------------ |
| 言語         | TypeScript                                     | 入力・ステージ定義・進行状態を型で扱い、ブラウザに配布する   |
| UI           | React                                          | ステージ情報、進捗、クリア画面を管理する                     |
| 3D描画       | Three.js                                       | カメラ、メッシュ、地面と穴の描画を直接制御する               |
| 3D物理       | Rapier 3D (`@dimforge/rapier3d-compat` を候補) | 重力、剛体、接触、傾きを扱う。WASM初期化を明示的に管理する   |
| 開発・ビルド | Vite                                           | React + TypeScriptの開発と静的ファイルへのビルド             |
| 検証         | Vitest / Playwright                            | 成長・配置などのロジックと、操作からクリアまでのブラウザ確認 |

初期案はクライアントのみ。バックエンドが必要になった場合は、用途を確認して TypeScript + Node.js + Express を検討する。
パッケージの具体的なバージョンとWASM読み込み方式は、導入時に公式情報と相互互換性を確認し、ロックファイルで固定する。
パッケージ・開発設定は試作用に作成済み。具体的な導入バージョンは `package.json` と `package-lock.json` に固定した。

## 比較した選択肢

| 選択肢                         | 評価                                                                                                                                    |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| Three.js + Rapierを直接利用    | 推奨。描画と物理の同期、特殊な床の衝突処理を明示的に制御できる。資源の破棄も自分で管理する必要がある                                    |
| React Three Fiber + Rapier連携 | Reactによる3Dシーン記述が便利。今回は独自の床更新・物理ループを先に検証するため、初期案には追加しない。性能が劣ると判断したわけではない |
| Babylon.js + Havok             | 描画・物理連携をまとめて扱える代案。移動する穴の床形状という課題は別途検証が必要                                                        |
| 2D表現と落下アニメーション     | 小規模にはできるが、穴の縁で物が傾いて落ちる3D物理の要求を十分に検証できない                                                            |

## 責務の分離

2026-10-26にPWA方式のオフライン起動を追加した。追加依存は使わず、Viteの出力後に配布物一覧と内容ハッシュを作ってService Workerへ埋め込む。Reactは保存状態と更新・再試行の案内を担当し、物理・成長・音声の処理は維持する。キャッシュと初回配信の条件は [offline.md](offline.md) を参照。

```text
React UI ← 進行イベント・低頻度の状態通知
                  ↑
Pointer入力 → ゲームループ → 穴の位置・物理世界 → Three.js描画
                  ↑
           ステージ定義・配置シード
```

- Reactは画面表示とライフサイクルを担当し、毎フレームの物体座標をReact stateへ送らない。
- ゲームループが入力、物理、回収、成長、クリアの順序を管理する。
- 進行ロジックは描画と分ける。成長閾値や回収の二重処理を独立して検証できるようにする。
- ステージデータは、物の種類・寸法・衝突形状・成長値、配置領域、目標物ID、成長表を持つ。
- ステージ切り替え時に物理世界、メッシュ、イベント登録を破棄し、重複ループや資源の残留を防ぐ。
- 最初は必要なモジュールだけを作り、汎用エンジンやECSは導入しない。

## 穴の移動とカメラ

物理世界では穴を水平面上で移動させ、地形と未接触の物は静止させる。
カメラの注視点を穴の中心に追従させることで、画面上では周囲が動いて見えるようにする。
世界全体を毎フレーム移動・縮小して物理状態を変える方法は使わない。

提案する透視投影では、穴半径を `R`、初期半径を `R0` としたとき、
同じ角度・画角のカメラ距離を `D = D0 × R / R0` とする。
穴の中心を注視点に保ち、同一画面寸法での穴の投影サイズを一定にする。
成長を滑らかに見せる場合は、表示用半径とカメラ距離を同じ比率で補間し、
物理半径との不一致が落下の見た目を壊さないか確認する。
端末の縦横比が変わった場合は、短辺に対する穴の占有率を基準に再計算する案とする。

入力は Pointer Events でタッチとマウスを共通化する。
操作領域に pointer capture を使い、`pointerup`、`pointercancel`、フォーカス喪失で操作を解除する。
画面方向から地面方向への変換と、カメラ後退時の移動量補正を一箇所で管理する。
ドラッグ方式の詳細はゲーム仕様の確認後に実装する。

## 最優先の技術検証: 穴を持つ床

黒い円を描くだけでは床の衝突形状は消えない。
物全体と床の接触を一括で無効化するだけでも、片側が縁に残る支持・傾きを表現しにくい。
落下の成立には、穴の開口部には床がなく、縁には支持できる衝突形状が必要。

初期の検証案は、平面から穴の領域を除いた固定床を三角形メッシュまたは凸形状の組合せで表現し、
穴の移動・成長に応じて必要な床形状を更新する方式。
円は多角形近似とし、描画の開口と衝突境界を揃える。
分割数、床全体の再生成と局所更新のどちらを使うかは、接触の安定性と更新費用を比較して決める。
試作では64分割の平面三角形メッシュを採用し、単純形状の落下・支持・傾きとChromiumでのクリアを確認した。
一般的な地形や複雑な形状、iPhoneでの負荷への適合性は未検証。

確認する挙動:

- 小物が落ち、穴より明らかに大きな物は縁に支えられる。
- 長い物が片側から傾いて落ち、角や縁で不自然に跳ねない。
- 穴が移動・拡大しても、床の継ぎ目や再生成で遠方の物が落ちない。
- 落下途中で穴が移動したとき、床が物体に再出現して押し戻す問題がない。
- 床更新による接触喪失、静止物の睡眠解除漏れ、床を動く台として扱うことによる引きずりがない。

RapierのJavaScript APIで確認できる PhysicsHooks は接触ペア・交差ペアのフィルター。
接触点ごとの変更APIを使えると仮定して設計しない。
床方式が成立しない場合は検証結果を提示し、方式の再検討や補助挙動をオーナーと相談する。

## 物理ループと物体管理

- 固定時間刻みで物理を進め、描画は `requestAnimationFrame` で行う。刻み幅は試作用仮値を定義する。
- 長い停止後に大量の物理ステップを実行しない。タブが隠れたら停止し、復帰時に入力と蓄積時間をリセットする。
- 物体には箱・球・単純な凸形状などを使い、描画メッシュと衝突形状を分ける。
- 仮ステージは単純形状の剛体と睡眠機能から始め、物を一律に毎フレーム起こさない。
- 床の支持が変わる物は明示的に起こし、穴の上で眠ったまま残る不具合を防ぐ。
- 回収後は剛体と描画を除去し、オブジェクトIDで加算を一度に限定する。
- CCDは高速移動時のすり抜けを確認して必要な物に適用する。

### 効果音・成長演出・動く物の改良

- 効果音はブラウザ標準のWeb Audio APIで合成し、最初の操作からAudioContextを作成・再開する。音のON/OFF、非表示時の停止、失敗表示、終了時の破棄を扱う。追加依存は使わない。
- 人の声は倍音を持つ音源と母音を表す3つの帯域フィルタで合成する。落下開始の状態変化で1回鳴らし、既存の音ON/OFF・停止・音源数制限に従う。終了時に声のフィルタと揺らぎ用音源も解放する。
- 人の母音は1.6秒へ伸ばし、後半は音量を下げて落下を表現する。アメリカの人の「Damn it!」は同梱WAVをAudioBufferへ読み込み、2つの単語を聞かせるため前半は音量を保つ専用の減衰カーブで再生する。音声の読み込みとデコードは共有し、失敗時は表示して音ボタンから再試行できる。ミュート・非表示・終了時は読み込み待ちの再生も無効にする。
- たぬきは2つの短い音源で0.5秒の鳴き声を合成する。エジプトの人は薄い箱の衝突形状と、YZ面に図形を押し出した板状モデルを使い、壁画のポーズを維持する。
- 成長演出はThree.jsの2つの輪と28個の粒子、Reactのレベル表示とバーの発光で表現する。物理半径とカメラ距離は従来どおり同時に更新し、表示径を一定に保つ。
- 各ステージに歩く種類を24体追加。シード付き方向変更・穴からの逃走・境界での反転を固定物理ステップで更新する。地表上では水平速度を制御し、落下開始時に直立制限と歩行制御を解除して剛体として落とす。
- 人・たぬきの描画は単純形状と歩行アニメーション。1つの箱型衝突形状を使い、歩行中の接触は物理演算へ任せる。経路探索は導入しない。

## ランダム配置と進行保証

4ステージは `stage.ts` の定義から目標・物・歩く種類・色・配置ポリシーを切り替える。群落と神殿跡の中心もシード生成し、地面の模様と物の配置で共用する。ピラミッドは凸の四角錐、丸太は横向きの円柱、タイヤは縦軸の円柱で外周を近似し、その他は箱型衝突形状。山の背景と発砲演出は物理世界へ追加しない。ステージ切り替えはゲームコントローラを破棄して再生成し、音の設定だけ維持する。

積み上げは場所を1回生成して段ごとの独立剛体を配置する。丸太の井桁積みは各段2本、段ごとに90度回し、山全体を囲む領域を予約する。通常の縦積みと同じ回収・睡眠解除を使い、追加ライブラリや配置の保存データは導入しない。

シード付き乱数で配置を再現可能にする。初期重なり、境界外、初期穴との干渉を検査する。
配置の再試行には上限を設け、失敗を握りつぶさず扱う。
各成長段階で入る物の合計ポイントが次の閾値を満たすように構成する。
ポイントが十分でも物理的に取れない場合があるため、到達可能性は実際のプレイでも確認する。
生成直後の検査と、穴の移動範囲・最終半径・目標物の寸法の整合性を保つ。

## 負荷・互換性の確認

成長ポイントの加算は1物体につき定数時間であり、基準の選択だけで物理負荷は解決しない。
小物が多い序盤、複数の物が落ちる中盤、巨大目標物と広い視界を持つ終盤をそれぞれ測る。

測定値はフレーム時間、物理ステップ時間、床更新時間、活動中の剛体数、描画数、資源の残留。
PCで60fps、対象iPhoneで30fps以上を暫定目標として提案する。対象機種と測定条件を決めてから評価する。
予算を超えた箇所に限り、局所的な物理有効化、空間分割、同形状の描画共有、描画解像度などを検討する。
遠方の物の固定化や更新省略は挙動を変え得るため、測定と副作用確認なしに適用しない。

Three.jsの WebGLRenderer はWebGL 2を使用する。
WebGL 2・WASMの初期化失敗、読み込み失敗、WebGLコンテキスト喪失をユーザーに分かる状態で扱う。
PC Chromiumでの成功をiPhone Safariの成功とみなさず、iPhone実機でタッチ・表示・性能を確認する。
