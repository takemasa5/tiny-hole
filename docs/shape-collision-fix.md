# 見た目にない部分で物が引っかかる問題の修正

更新日: 2026-11-07

## 原因

成長版の追加モデル（家具・玩具・巨大物など）は外接する一つの箱を当たり判定としていた。机の脚の間、照明の支柱の周囲、ヒーローの脚の間など、見えていない空間も穴の縁に支えられていた。従来モデルにも箱型や全体の凸形状が残っていた。

また、登録寸法だけを使って物の中心を床上に置いていたため、登録寸法と実モデルの高さが違う物は初期状態で一部が床にめり込んでいた。落下完了も傾いた外接箱で判定していたので、実モデルが落ちきっても回収が遅れる場合があった。

## 変更

- 全8ステージの成長版で、実際に表示するモデルの各立体部品から凸形状を作り、一つの剛体に複数の当たり判定を付ける。脚の間などの空間を埋めない。
- 輪状のナット・タイヤは輪に沿って分割し、パズルやエジプトの板状人物は押し出し形状の三角柱に分割する。くぼみや中央の穴を全体の凸形状で塞がない。
- モデル内に焼き込まれた変形、親子の座標変換、インスタンス化した窓も反映する。厚みのない塗装用の面は支持面にしない。
- 初期配置・補充・目標物の置き直しは実モデルの下端を使う。傾いた物の落下開始・床下判定・回収判定も、同じ形状の上端・下端を使う。上下非対称のモデルも中心から対称として計算しない。
- 床下に入った物の全ての部品について床との接触を外し、撤去時も全ての部品を解放する。
- 歩行する手足は落下時に通常姿勢へ戻す。特撮の攻撃用の腕も落下時に戻し、落下中の見た目と剛体の形状をそろえる。
- 形状は種類・ステージ・寸法ごとに再利用する。物理演算中に表示用モデルを毎回作り直さない。

成長段階・寸法・加点・配置のテーマは変更していない。レベル不足でも実際に飲み込めたら回収・クリアする扱いは維持する。穴より大きい実部品が縁に支えられる場合は、引き続き物理演算で支えられる。

## 検証

- 自動テスト336件（26ファイル）。追加した19件では、脚の間・パズルのくぼみ・輪の中央の空間、実部品の接触、縮尺0.01・1・100の照明の落下、全8ステージの各種類の傾いた実モデルと当たり判定の上端・下端・外周の一致を確認する。
- 各ステージ12段階で穴の中の物が落ち、隣の物が床に支えられる確認、サイズ不足の物の傾き、レベル不足の最終目標の実回収も継続して確認する。丸い物や上部が重い物が横倒しで床に落ち着くこともあるため、隣の物は直立姿勢の中心高さではなく実形状の下端と上端で支持を確認する。
- Chromiumの比較場面で、穴の半径0.65・照明の幅1・高さ3の条件を同じにして180ステップ進めた。旧箱型は床上に残り、部品ごとの当たり判定では落下した。[結果](../reports/shape-collision-2026-11-07/models/results.json) / [重ね描き](../reports/shape-collision-2026-11-07/models/collider-overlay.png)。これは比較用の場面であり、通常ゲームの操作確認とは別。
- Chromiumで会社の机の透過と復帰、ドラッグ終了後の停止、閉じた境界、再開を確認。[結果](../reports/shape-collision-2026-11-07/interactions/results.json)。
- Chromiumの390×844・タッチ入力で、おもちゃの移動・停止・箱の境界・再開・ステージ切り替えを確認。[結果](../reports/shape-collision-2026-11-07/mobile/results.json)。
- Chromiumで、おもちゃステージを通常のドラッグ・キー操作で全12段階・5空間を通ってクリアし、次の会社ステージへの切り替えまで確認。道路と線路の動作、各扉の開閉も確認。[結果](../reports/shape-collision-2026-11-07/toys-flow/results.json)。各段階の記録時点では接触形状307〜763個、フレーム時間の中央値約16.7ms・p95約16.7〜16.8ms。これはPCの記録であり、全フレーム・全配置の保証ではない。
- ビルド・Lint・変更ファイルのPrettierが成功。今回の修正後のiPhone実機・WebKitは未確認。PCのフレーム時間はiPhoneの性能を示すものではない。

## 範囲と制約

立体の部品ごとに凸形状を作る方式であり、任意の新しい凹形状を自動で正確に分割するものではない。現在の凹形状は輪と押し出し形状を専用に分割する。新しい凹形状を追加する際は、同様に部品へ分ける必要がある。歩行・攻撃中の手足は演出で動き、落下時には剛体用の姿勢に戻る。

単一の箱から複数部品へ変わるため、剛体数に加えて接触形状数も検証結果へ記録する。描画設定や物理エンジンの許容誤差、依存関係は変更していない。
